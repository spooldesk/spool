# Contributing to Spooldesk

Thanks for taking a look. This file covers how to get it running, what the tests
expect, and the handful of traps that are not obvious from reading the code.

## Running it locally

```bash
python -m venv .venv
source .venv/bin/activate                       # Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install --require-hashes --only-binary=:all: -r requirements.txt -r requirements-dev.txt
cp .env.example .env                            # Telegram credentials are optional
python scripts/seed_demo_data.py                # synthetic content to look at
python scripts/run_demo_dashboard.py            # http://localhost:8010
```

The demo defaults to `admin@local` / `admin` (unless `ACCESS_PASSWORD` is
already set in the process environment).

**Python 3.12** — the version the container ships and CI runs.
The runtime and test dependencies are pinned with hashes. Update their `.in`
inputs and regenerate the locks using [the dependency workflow](docs/DEPENDENCIES.md).
Changing the supported Python version requires checking wheels and the test suite.

Normal installations run the dashboard and its channel workers against
PostgreSQL. The explicit synthetic demo above uses disposable SQLite storage.
Telegram is optional; the legacy standalone bot is not required for a new
installation. Never run the demo seed against a real installation.

## Tests

```bash
pytest
```

The suite uses a temporary database and mocked channel deliveries. CI also
runs it against PostgreSQL. Test order is not randomised by the current
development dependencies; keep fixtures independent of execution order.

Two guards are worth knowing about before they fail on you:

- **No Cyrillic in the English UI.** `tests/test_dash_i18n.py` renders every page
  and fails on a Cyrillic character that is not operator-entered data.
- **No Cyrillic literals in `src/`.** `tests/test_no_hardcoded_language.py`
  parses every module. Three files are allowlisted by name because their
  Cyrillic is data being matched, not text being shown — the credential
  scrubber, the acknowledgement filter, and the AI prompt.
- **English for newcomers.** Every markdown file, the compose file, the
  Makefile and `scripts/setup.py` must read as English: they are what someone
  meets before they ever see the UI.
- **Locale parity.** Every key must exist in both locales. Adding an English
  string without its Russian counterpart fails the suite.

## Two separate translation systems

They are easy to confuse, and confusing them ships the wrong language to the
wrong person:

| | Follows | Used by | Reached via |
|---|---|---|---|
| `src/utils/i18n.py` | the **customer's** language (ru/uk/en) | bot messages to users | `get_text(key, lang)` |
| `src/dashboard/i18n.py` | the **operator's** UI language (en/ru), with an instance fallback | dashboard text | `t(key)` |

A customer writing in Ukrainian must get Ukrainian regardless of what the
dashboard is set to, and vice versa.

## The stylesheet needs Node — which is why it is committed

`src/dashboard/static/tw.css` is a **compiled, committed** Tailwind build. That
is deliberate: deployments need no Node toolchain. The cost is that **a Tailwind
class not already in that file silently does nothing.** No error, no warning —
the element just renders unstyled, and you will not notice unless you look.

If you add a utility class that is not already used somewhere, rebuild:

```bash
tailwindcss -c tailwind.config.js -i src/dashboard/static/tw.input.css \
            -o src/dashboard/static/tw.css --minify
```

(standalone CLI v3.4.x, no npm install needed). If you have no Node, check
whether an equivalent class is already in the build and use that instead:

```bash
grep -F 'max-w-\[170px\]' src/dashboard/static/tw.css
```

Light-mode colours are the exception: they live in `src/dashboard/static/app.css`
as a palette inversion, so they need no rebuild. Content templates are written
in one dark idiom and that file remaps it. Aim for at least 4.5:1 contrast on
body text in both themes.

## Screenshots

`demo_screenshots/` is regenerated, never edited by hand:

```bash
pip install -r requirements-screenshots.txt
playwright install chromium

python scripts/capture_screenshots.py     # reseeds, serves, shoots
python scripts/capture_board_gif.py       # the board animation
```

Those two live in their own requirements file rather than in the dev one, so
CI does not install a browser automation stack it never uses.

Both reseed first on purpose: the demo queue ages in real time, and an hour
after seeding every waiting card has slipped past its target — honest behaviour,
useless photograph.

## Conventions

- **No real data, ever.** Everything in the repo is generated by
  `scripts/seed_demo_data.py`. Screenshots, fixtures, examples — all synthetic.
- **Comments explain why, not what.** If a line is surprising, say what would
  break without it.
- Database migrations are additive and applied in place at startup, see
  `src/database/db.py`.
- Anything an operator can see is a translation key, not a literal.

## Pull requests

Small and focused beats large and sweeping. Say what breaks without the change —
a failing test that now passes is the clearest possible version of that. If it
touches the UI, a before/after screenshot saves a round trip.
