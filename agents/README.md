# Codex Lead → Claude Code worker

Это локальные инструкции и один Python-скрипт, без сервиса, БД и постоянно
работающих агентов. Codex ставит задачу, вызывает CLI, получает ответ в текущей
сессии и самостоятельно принимает результат. Пользователь ничего не копирует.

## Как Lead решает, нужен ли worker

| Задача | Решение |
|---|---|
| Rename, форматирование, простой CRUD, очевидный небольшой bugfix | Lead выполняет сам |
| Ограниченное исследование, независимое ревью, существенная подзадача | До одного worker, если польза больше затрат на передачу контекста и проверку |
| Большая задача с двумя независимыми направлениями | До двух workers с отдельными workstream и общим parallel_group |

В `delegation_reason` Lead пишет, какую пользу получит, в `context_cost_reason`
— почему выбранного объёма контекста достаточно. Примеры пользы: независимая
проверка рискованного решения, анализ незнакомого контракта параллельно полезной
работе Lead. Само наличие Claude не является основанием для вызова.

| Роль | Сейчас |
|---|---|
| `researcher` | Чтение выбранного снимка, исследование, вопросы и ограничения |
| `security_reviewer` | Проверка выбранного решения/кода, доказательные замечания |
| `qa_test` | Анализ покрытия и сценариев; тесты запускает Lead |
| `backend_implementation` | Реализация через проверяемые файловые артефакты в отдельном worktree |
| `frontend_implementation` | Реализация через проверяемые файловые артефакты в отдельном worktree |

Роли существуют только на время задачи. Рекурсивное делегирование запрещено.

## Использование из текущей сессии Lead

Python из проекта на Windows: `.venv\Scripts\python.exe`. В примерах ниже
`python` означает этот интерпретатор либо доступный Python 3.12+.

```powershell
python scripts/claude_worker.py check
python scripts/claude_worker.py prepare agents/tasks/orchestration-smoke.json
python scripts/claude_worker.py run agents/tasks/orchestration-smoke.json
python scripts/claude_worker.py history --task-id orchestration-smoke
```

`check` проверяет существующий CLI и обязательные flags. Ничего не устанавливает,
не меняет PATH/settings и не вызывает модель. При отсутствии CLI Lead останавливает
делегирование и сообщает, что нужно установить/авторизовать Claude Code и сделать
`claude` или `claude.cmd` доступным в PATH. В текущей npm-установке Windows wrapper
указывает на native `claude.exe`: runner использует именно его для надёжной передачи
пустого списка tools. Неизвестный shell wrapper не исполняется автоматически.

Lead создаёт задачу по `task.example.json`. Разовые задачи с приватным описанием
нужно хранить в игнорируемом `.agent-runs/tasks/`, а не коммитить. Структура:

- `id`, `role`, `mode`, `complexity`;
- `goal`, `context`, `relevant_paths` (файлы или небольшие каталоги);
- `constraints`, `acceptance_criteria`, `allowed_changes`, `forbidden_changes`;
- `delegation_reason`, `context_cost_reason`;
- только для двух workers: `parallel_group`, разные `workstream`, `parallel_reason`.

Для read_only `allowed_changes` строго `[]`. Для implementation — 1–6 явных файлов и точный `base_commit` (40 hex). `prepare` показывает manifest: пути, размеры,
SHA-256; модель не вызывается. Lead проверяет файлы и достаточность контекста.
Лимиты: 12 файлов, 24KB на файл, 48KB исходников и 12KB описания задачи. Номера
строк добавляются при передаче. Превышение вызывает отказ, не молчаливое усечение.

`run` отправляет структурированную задачу и выбранный текст через stdin. На выходе
— JSON с фактическим ответом Claude, номером попытки и `pending_lead_review`.
CLI использует текущую доступную авторизацию/модель; runner не задаёт новую модель
и не подключает платные услуги. Default timeout — 180 секунд, верхняя граница 600.
Передаётся CLI budget cap $1 (максимум $5 через аргумент); это не обещание точного
списания или эквивалента лимита подписки. Фактическую оценку возвращает CLI.

Режим запуска: `--print --safe-mode --strict-mcp-config --no-session-persistence
--tools "" --permission-mode dontAsk --output-format json`. Claude работает
в отдельной временной папке. Нет Read/Edit/Bash/Agent/Task/MCP tools. Поэтому
все нужные исходники передаёт Lead; Claude не может сам расширить исследование.
`CLAUDE.md` передаётся явно, поскольку safe mode отключает его автоматическую загрузку.
Автообновления отключены переменными окружения только дочернего процесса.

Это ограничение возможностей доверенного установленного CLI, не отдельная OS
sandbox. Административные политики CLI сохраняются. Runner не меняет настройки
авторизации и не обещает удаление серверной истории провайдера. Локальное сохранение
сессии отключено; полные prompt/response runner на диск не пишет.

## Лимиты, ошибки и журнал

Одновременность контролируют два OS file locks в `.agent-runs/`. Default — один.
Оба параллельных вызова должны иметь `--allow-second-worker`, большую задачу,
одинаковый `parallel_group`, разные `workstream` и обоснование независимости.
Третий процесс получает отказ. Это лимит запускателя в данной рабочей копии;
Lead не обходит его прямыми вызовами CLI или запуском из другой копии.

Повтор того же task ID запрещён без `--retry-reason "конкретная причина"`.
Не создавать новый ID ради обхода учёта. Автоповторов модельного вызова runner
не делает; сетевые повторы внутри самого Claude CLI контролирует CLI.
Timeout останавливает созданный процесс/его дерево. OS locks снимаются при выходе
runner; после принудительного уничтожения самого runner Lead обязан проверить,
не остался ли его CLI-процесс, прежде чем запускать следующий.

JSONL-журнал `.agent-runs/delegations.jsonl` содержит:

- `started`: task ID, краткую цель/причину, роль, manifest, attempt/repeat_count;
- `returned` или `failed`: краткий результат/тип ошибки, время, digest ответа,
  оценку стоимости CLI, статус ожидания приёмки;
- `lead_review`: принятие/отклонение и доказательства Lead.

Полные prompts/responses и credentials не логируются. Известные формы токенов
и приватных ключей блокируются на входе; `.env`, скрытые каталоги, локальные
данные, gitignored paths, symlinks/junctions, бинарные и слишком большие файлы
не допускаются. Проверка шаблонов не распознаёт все возможные секреты: Lead
обязан осмотреть выбранный контекст. В журнал нельзя писать приватные данные.

Ошибка/невалидный JSON не превращаются в успех. Исходники снимка хешируются до
и после ответа; изменение означает устаревшую основу ревью и требует проверки.
Даже валидный ответ никогда не принимается автоматически.

```powershell
python scripts/claude_worker.py accept --task-id orchestration-smoke --attempt 1 --decision accepted --evidence "Lead checked cited rules and source hashes; isolated infrastructure tests passed."
```

Lead сверяет выводы с файлами, проверяет diff и запускает необходимые тесты.
Если worker сообщил нехватку данных, Lead дополняет конкретный контекст и
обосновывает повтор, либо заканчивает задачу самостоятельно.

## Реализация через worktrees

Пользователь разрешил implementation workers. Claude пишет код в JSON `changes`
(полные тексты разрешённых файлов); runner проверяет весь список до записи и
помещает файлы только в отдельный git worktree с веткой `codex/worker/<id>-<attempt>`.
Это намеренно ограниченный исполнитель: прямых Read/Edit/Bash tools нет.
Модель не может читать секреты, запускать команды или расширять write allowlist.

Задача использует mode `implementation`, роль backend_implementation либо
frontend_implementation, base_commit = точный текущий HEAD и allowed_changes
из 1–6 файлов src/tests/assets/docs. Существующий целевой файл обязательно
входит в relevant_paths. Максимум 24 КБ на файл и 32 КБ на JSON-ответ.
`prepare`, `run`, лимиты стоимости и учёт повторов общие с review-задачами.

Worktree создаётся без полного checkout: материализуется только выбранный
контекст. Незакоммиченные изменения выбранных файлов копируются как baseline,
основное дерево не коммитится и не очищается. Поэтому обычный diff с HEAD
не является patch worker. Сравнивайте выбранные файлы с baseline SHA-256 из
`.agent-runs/<task>-<attempt>-implementation.json`. Все linked worktrees
используют журнал и OS locks исходного Git-репозитория.

Lead читает код, проверяет каждый baseline hash перед интеграцией и запускает
тесты в изолированном окружении. Только затем переносит разрешённые изменения
и записывает accept с доказательством. Нельзя cherry-pick непроверенный worktree,
давать модели сеть/реальные данные или автоматически исполнять её команды.
Worktree сохраняется для ревью; удаление только после приёмки и проверки результата.
При ошибке worktree может оставаться в списке `git worktree list`: не удаляйте
его принудительно без осмотра. Полные тексты файлов нужны для интеграции; в журнал
по-прежнему идут только краткий итог и хеши, а не полные prompts/responses.

## Проверки и удаление инфраструктуры

```powershell
python -m unittest discover -s tests/agents -p "test_*.py" -v
```

Тесты используют временные папки/fake CLI, без модели, app DB и сетевых вызовов.
Реальный smoke запускается вручную самим Lead через команду `run` выше, когда
это требуется пользователем или после существенного изменения механизма.

Инфраструктура состоит из `AGENTS.md`, `CLAUDE.md`, `agents/`, одного runner,
`tests/agents/` и игнорируемого журнала. Удаление этих файлов и добавленных ignore
правил отключает её; приложение Spooldesk от них не зависит. Журнал можно
архивировать отдельно. Не удаляйте lock-файлы во время активного запуска.

Основания: [постоянные инструкции Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md),
локальный `claude --help` (проверен 2.1.278),
[управление обновлениями Claude](https://code.claude.com/docs/en/setup).
