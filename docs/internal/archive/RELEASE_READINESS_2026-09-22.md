# Spooldesk: готовность к первому self-hosted выпуску

> Исторический срез до обновления PostgreSQL, переписки и жизненного цикла
> операторов. Актуальные изменения, проверки и оставшиеся условия выпуска:
> [Product upgrade — 22 September 2026](PRODUCT_UPGRADE_2026-09-22.md).
> Оценка 80% ниже относится к прежнему состоянию.

Дата: 22 сентября 2026. Актуализирует отчёты от 17 и 20 сентября.
Целевой формат: отдельная установка на инфраструктуре клиента, необязательное
платное внедрение и сопровождение. Telegram — один из каналов, а не основа
позиционирования. Публичный SaaS не входит в этот выпуск.

**Ориентир — около 80% готовности к первому публичному self-hosted выпуску.**
Это экспертная оценка оставшегося объёма, не измерение качества, вероятности
отказа или подтверждение готовности к реальным данным. Функциональное ядро уже
существенно готово; незакрытые release gates перечислены ниже. До их прохождения
формат — проверяемый кандидат и согласованные пилоты, а не обещание безусловной
production-ready установки любому клиенту.

## Завершено на этом этапе

- Новый лендинг на английском (`/`) и русском (`/ru/`). Общий шаблон, отдельные
  словари, проверяемая генерация. Авторская типографика, интерактивная схема
  каналов, реальные скриншоты с демонстрационными данными, переключение кадров,
  анимации появления и поддержка reduced motion. Основной контент, ссылки и FAQ
  не требуют JavaScript.
- Предложения: self-hosted $0 в рамках существующей лицензии; начальное
  предложение внедрения $300; сопровождение $149/месяц с ограниченным объёмом.
  Инфраструктура и провайдеры оплачиваются отдельно, сроки/состав согласуются.
  Убраны доступный Cloud signup, включённый AI и неподтверждённый live demo.
  Лицензия не менялась. Спрос и цены ещё предстоит подтвердить продажами.
- Экспорт сайта содержит только девять публичных файлов. Внутренние отчёты из
  `docs/` не публикуются вместе с лендингом. Есть готовый локальный ZIP и
  [инструкция сборки/Cloudflare](../../LANDING.md).
- Backup дополнительно обнаруживает обычные изменения состава/метаданных
  вложений во время копирования. Это проверка ошибочно оставленного writer,
  а не замена остановке пишущих процессов или файловому snapshot.
- Ошибка внешнего копирования удаляет созданный этим запуском `.part`, сохраняя
  хорошую локальную копию. Незавершённый backup не отмечается успешным.
- CI проверяет обе версии сайта, сохраняет публичный artifact, запускается
  также на существующей ветке `staging`. Добавлен ручной выпуск кандидата:
  архив исходников с commit SHA, проверенный контейнер, image ID и контрольные
  суммы; итоговая упаковка зависит от всех jobs. Без автоматической публикации.
  См. [RELEASING.md](../RELEASING.md).
- README согласован с реальным предложением. В DEPLOY исправлен совет
  пересоздать базу при 500: сначала диагностика и сохранение данных.

`spooldesk:release-check-20260920-1745`, поверх которого **только для теста**

кода, а не новый опубликованный image. Хеши снимка и результат сохранены локально

## Что ещё обязательно до публичного релиза

1. **Зафиксировать и проверить финальный commit.** Сейчас есть большой набор
   незакоммиченных изменений нескольких этапов. Нужны ревью, безопасный commit,
   PR и успешный удалённый CI именно итоговой версии. Новая упаковка кандидата
   описана и проверена локально по структуре; в GitHub ещё не выполнялась.
2. **Пройти путь клиента из release artifact.** Скачать полученный кандидат,
   проверить контрольные суммы, установить на чистые volumes по инструкции,
   выполнить preflight и сценарий виджет → ответ → вложение → закрытие.
   Затем присвоить версию и опубликовать проверенный выпуск. Доступного
   опубликованного release/digest этот этап не создал.
3. **Проверить реальные интеграции на выделенных тестовых аккаунтах.** Для
   email: SMTP/IMAP, входящее и исходящее, вложения, References/Message-ID,
   повтор после сбоя. Для Slack/Telegram — аналогичный smoke с тестовыми
   адресатами. Поддельные сетевые ответы в тестах не доказывают настройки
   провайдера. Не использовать переписку реальных клиентов для таких проверок.
4. **Проверить эксплуатацию конкретной установки.** HTTPS/домен, внешний
   мониторинг и получатель тревог, внешнее хранение backup, сохранённый ключ,
   восстановление с этого хранилища. Для PostgreSQL уже проверен dump/restore
   БД, но общий сценарий DB + attachments + key + HTTP на выбранной PostgreSQL
   установке нужно выполнить перед её передачей. Для обновлений существующих
   установок требуется отдельный rehearsal отката к pre-upgrade backup.
5. **Опубликовать витрину и подготовить первый пилот.** Проверить доступность
   `hello@spooldesk.net`, загрузить публичный сайт на Cloudflare, проверить обе
   версии на HTTPS. Согласовать объём, часы работы, стоимость и условия оплаты
   услуг. Провести первые внедрения и измерить поддержку/повторное использование.

Свой VPS продавцу self-hosted не обязателен. Локальный изолированный стенд уже
позволяет проверять код и восстановление. Публичный лендинг размещается отдельно;
приложение, БД и файлы работают на инфраструктуре выбранной клиентом установки.

## Функциональные приоритеты после этих gates

Для первого self-hosted пилота не нужны SaaS billing, общая tenant-БД или новая
система агентов. Сначала получить живую проверку существующего рабочего цикла.
Затем по результатам первых установок выбрать улучшения onboarding и диагностики,
импорт данных из системы клиента и автоматизацию обновлений. Не обещать импорт
или дополнительные интеграции как часть стандартного внедрения до оценки.

Критерий коммерческого продолжения: три оплаченных внедрения с измеренными
трудозатратами и первые добровольные продления сопровождения. Это цель проверки
спроса, не прогноз выручки. SaaS имеет смысл оценивать после подтверждённого
запроса на размещение у нас и понятной стоимости эксплуатации.
